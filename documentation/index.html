Agentic Coding Template

A repository template for building software with coding agents, in which you keep the decisions: agents plan, implement, and review each other, scripts check and record, and nothing reaches main without evidence and a human merge.

What it is

The template is a set of Bash scripts, agent prompts, and policies that you copy into a new repository. It needs Git, the GitHub command line, jq, and at least one coding agent on your machine. It does not prescribe a language, a framework, or a model: the implementer, the reviewer, and the planner are each configured as an agent and a model, and you can change them per project or per run.

You decide what is built

Requirements and the roadmap are approved by you, and the approval is bound to the exact documents. An agent cannot rewrite them on the way.

Whoever writes does not review

Every planning and every feature is read by an independent agent that cannot edit anything, preferably another model than the one that wrote it.

Evidence, not assurances

One command runs the project's checks. Reviews, triage decisions, and verification are recorded for the content they apply to and go stale when it changes.

Git and GitHub are the record

One Issue, one branch, one worktree, and one pull request per feature. What was decided, and why, is where the team already looks.

How it came about

The template started in September 2026 from a practical question: how do you let a coding agent do real work on a project without losing track of what it did, and why? The first version was small: instructions for agents in AGENTS.md, a plan-act-evaluate rhythm, a worktree per task, a read-only reviewer, CI, and human gates sized to the risk of a change.

From there it grew by use. Each step of the workflow began as something done by hand, was written down, and became a script once it was clear what the script had to guarantee. Three experiences shaped it most:

  • Unclear goals cost more than slow code. A planning round that questions the idea before anything is designed, the Project Grill, removed most of the rework later. The requirements it produces are approved by a person, and the plan is reviewed before the first feature starts.
  • An agent that checks its own work finds little. Independent review with structured findings, an explicit answer to every finding, and a new review after the fixes turned out to be where most real defects were caught.
  • A model cannot be the judge of its own risk. Whether a change needs the owner is decided first by rules about the files it touches. The reviewer's judgment is added on top and can only make the gate stricter.

The template was built alongside a real project, a physics course site with executable lessons and formal proofs. Running dozens of its features through the workflow, many of them unattended overnight, is what exposed the weak spots: stale reviews after a base branch moved, runs that stopped for a network error, checks that an agent could quietly weaken. Each became an Issue in the template, and most of the scripts carry a test for the case that went wrong.

What it deliberately is not

Several larger frameworks for agentic development were studied along the way; Research and comparisons lists them and what was taken from each. The template stays one small, auditable workflow, not a stack of frameworks:

  • It is not an orchestration platform. There is no always-on swarm, scheduler, or registry to run before a small project can start.
  • It does not open the whole roadmap as Issues. A feature Issue is created just in time, when the project knows what it has learned.
  • It does not make test-first a ritual for every edit. The requirement is meaningful evidence that runs.
  • It does not merge or deploy by itself. The unattended run ends at an open pull request.
  • It does not treat a Git worktree as a sandbox. A worktree separates files, not databases, ports, or credentials.
