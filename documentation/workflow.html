The workflow

A project is planned once and approved by you. After that, every feature of the roadmap goes the same way: its own Issue, its own worktree, an independent review, and one pull request that you merge.

The overview shows the whole route. Select "Project planning" or "Feature work" to open the steps inside it, with the loops back to an earlier step; select a step there to see which script runs it, what goes in and comes out, who decides, and when it stops. Everything is also on this page, below the overview.

You decide or approve An agent works A script checks or records
  1. Project ideayour description
  2. Project planninggrill, plan, review, revise
  3. Planning approvedmerged by you
  4. Feature Issueone roadmap feature
  5. Feature workimplement, review, fix
  6. Mergepull request, by you
  7. next roadmap feature
  8. the planning has to change: change cycle

The two phases, step by step

The blocks marked with ▸ in the overview contain these steps.

1 · Project planning

Once per project, in the planning worktree.

  1. Project ideaYou describe what you want to build
  2. Project Grill and requirementsstart-planning.sh · questions, then your approval
  3. Planner writes the planningarchitecture, roadmap, decisions
  4. Independent planning reviewreview-planning.sh · read-only
  5. Decide on the findings, reviserevise-planning.sh · your approval
  6. Final approvalfinish-planning.sh · bound to the exact documents
  7. Planning pull request mergedthe approved planning is on main
  8. findings adopted: review again

2 · Every feature

Per roadmap feature, in its own worktree and branch.

run-feature.sh runs the steps from the implementation to the open pull request without you, with at most five review rounds. It never merges. Details

  1. Feature Issuecreate-feature-issue.sh · just in time
  2. Implementationstart-feature.sh · own worktree
  3. Verificationverify.sh · the project's own checks
  4. Independent feature reviewreview-feature.sh · read-only
  5. Triage of the findingstriage-review.sh · your approval
  6. Fixesapply-triage.sh · only what the triage says
  7. Commit with evidencefinish-feature.sh · review and gate recorded
  8. Pull request and CIpublish-feature.sh
  9. Mergeyou, or what the merge gate allows
  10. fixed: review the changes again

After a merge the next roadmap feature starts at "Feature Issue". When the planning itself has to change, a change cycle leads back to the planning.

Three ways to work

The steps are the same every time; what differs is who starts them. Choose per feature: a risky or unclear feature step by step, routine work with one command.

WayYou doRuns by itselfEnds atChoose it when
Step by step Run each script, follow the agent in its session, approve the triage and the commit message One step at a time Wherever you stop The feature is risky, the requirements are unclear, or you want to learn what the workflow does
One command per feature Start run-feature.sh for an Issue; afterwards read the pull request and the triage decisions that were approved without you, and merge Implementation, review, triage, fixes, commit, and pull request, with at most five review rounds An open pull request, or a stop with its reason The Issue is clear and the feature is routine
A supervised queue of features Agree on a rule for merging, and decide what the gate holds back A supervising agent starts several runs side by side, restarts what stopped on a temporary fault, brings branches up to date, and merges what the rule allows Merged features, and a list of what waits for you Several independent features are ready and you are away

The first two are the template. The third is how it was used on a real project, with a coding agent as the supervisor and a few helper scripts of that project; the template has no queue of its own. The merge rule there was: the last review passed, CI is green on a branch that contains the current main, and the commit records that the owner's approval is not required. A ready queue and parallel runs that avoid each other's files are among the possible improvements.

Every step in detail

Project planning

You

Project idea

The planning starts from a short description in your own words. It does not have to be complete: the next step asks what is missing.

Goes in
PROJECT_DESCRIPTION.md, written by you
Comes out
The starting point of the planning; the file is never rewritten by an agent

You, questioned by an agent

Project Grill and requirements

An agent questions you about goals, users, scope, and what is deliberately left out, until the open ends are named. It writes the requirements; nothing is planned before you approve them.

Script
./scripts/start-planning.sh <name>
Goes in
The project description and your answers
Comes out
docs/PROJECT_REQUIREMENTS.md in the planning worktree planning/<name>
Human gate
You approve the requirements before the planner starts

Planner agent

Planner writes the planning

From the approved requirements the planner writes the architecture, a roadmap of features with stable IDs and dependencies, and a decision record for each choice that is hard to reverse. The roadmap states intent; it is not a backlog of Issues.

Script
The same run of start-planning.sh
Comes out
docs/architecture.md, docs/roadmap.md, docs/decisions/
Stops when
The planner has a question only you can answer; it is recorded, not guessed

Planning reviewer, read-only

Independent planning review

A second agent, preferably another model, reads the planning without being able to change it. Its findings are structured data that a script validates, so a later step can tell whether each one was answered.

Script
./scripts/review-planning.sh
Comes out
A review record with findings by severity, and a readable report
Next
Findings: decide on them. No findings: final approval

You, on a proposal of the planner

Decide on the findings, revise

The planner proposes a decision per finding: adopt, reject, defer, or escalate to you. You approve the decisions, and only then are the documents revised. A revision that changes the planning makes the review stale, so the review runs again.

Script
./scripts/revise-planning.sh
Human gate
You approve the decisions; an escalated finding needs your answer
Loop
Back to the planning review until a round changes nothing

You

Final approval

Your approval is recorded together with a fingerprint of the documents you approved. A later change to the requirements or the roadmap makes it stale; an update of the architecture by a feature does not.

Script
./scripts/finish-planning.sh
Comes out
docs/PLANNING_APPROVAL.md and the planning commit
Refuses when
The latest review is stale or has an unresolved escalation

You

Planning pull request merged

The planning reaches main through a pull request like any other change. From here on, features can start.

Comes out
An approved planning on main

You, then the same loop

Changing an approved planning

An approved planning is not edited by hand. You write a short change request, the planner changes only what the request needs, and the review, the decisions, and your approval follow as before. A changed requirement is questioned first with --grill. Feature IDs stay stable, and a decision record is superseded, not removed.

Script
./scripts/start-planning.sh <name> --change <file>
Small amendment
./scripts/finish-planning.sh --amend for the architecture and decision records only
Meanwhile
No new feature Issue is created until the change is approved and merged; features in progress continue

Every feature

Script

Feature Issue

One feature of the roadmap becomes one GitHub Issue, created when you are about to build it. The roadmap is not turned into a backlog of Issues in advance: by the time a late feature starts, the project has learned things its Issue should know.

Script
./scripts/create-feature-issue.sh F01
Goes in
The roadmap entry of the feature
Refuses when
The planning approval is not current

Implementer agent

Implementation

The feature gets its own Git worktree and branch, so several features can be in progress without touching each other. The implementer reads the Issue, the architecture, and the accepted decisions, then writes the code, the tests, a summary of the changes, and a handoff note for whoever continues.

Script
./scripts/start-feature.sh <issue>; --resume continues an interrupted session
Comes out
Uncommitted work in feature/<issue>-<slug>
Stops when
The agent needs a decision of yours: it ends as blocked with its question in the handoff note

Script

Verification

The checks of the project (tests, linters, builds) are declared in one file and run by one command, locally and in CI. A pass is recorded for exactly the content that was checked, so a later step can rely on it without running everything twice.

Script
./scripts/verify.sh, configured in scripts/verify.conf
Rule
No review of work that does not pass, and no commit either

Reviewer, read-only

Independent feature review

A reviewer that did not write the code, preferably another model, reads the complete change against the Issue. It cannot edit anything. It reports findings by severity, gives a verdict, and classifies the impact on the architecture, which the merge gate uses later.

Script
./scripts/review-feature.sh <issue>; --changes reviews only what changed since the previous round
Comes out
A review record bound to the reviewed content; a change afterwards makes it stale
Next
Findings: triage. No findings: commit

You, on a proposal of an agent

Triage of the findings

Not every finding has to be fixed now, but every finding gets an explicit answer: fix now, defer to a follow-up Issue, or accept with a reason. The approved triage is published on the feature Issue, so the decision is on record where the work is discussed.

Script
./scripts/triage-review.sh <review>
Human gate
You approve the triage; in an unattended run the triage agent's proposal is published for you to read afterwards

Implementer agent

Fixes

The implementer resolves the findings the triage marked "fix now" and nothing else. It cannot change the review or the triage it works from. After the fixes the review runs again, on the changes only.

Script
./scripts/apply-triage.sh <triage>
Loop
Back to the review until a round passes

Script

Commit with evidence

The commit is made by a script that first checks that verification passes and that the latest review is current and resolved. The message records the review result, the verification, and whether the merge needs the owner's approval, for exactly this content.

Script
./scripts/finish-feature.sh <issue> "<summary>"
Never
Pushes or merges

Script

Pull request and CI

The branch is pushed and one pull request is opened that closes the Issue. CI runs the same verification as the local command.

Script
./scripts/publish-feature.sh <issue>
Comes out
An open pull request with the evidence in its description

You

Merge

Merging is a human decision. A change of a decision record, of a protected path, or with an impact the reviewer calls major or breaking always waits for the owner; the rules are read from the base branch, so a feature cannot relax the gate it is checked by.

Script
./scripts/check-guardrails.sh decides what needs the owner
Afterwards
./scripts/cleanup-worktree.sh <issue> removes the worktree

Script, driving the agents

One command for a feature

run-feature.sh runs the implementation, the review, the triage, the fixes, the commit, and the pull request in order, without questions. The script, not an agent, decides whether a step succeeded: it retries what looks temporary, lets the implementer repair a verification that fails twice, and stops with a clear reason otherwise.

Script
./scripts/run-feature.sh <issue>
Limits
At most five review rounds; it ends at an open pull request and never merges
Stops when
An agent needs your decision, a step keeps failing, or the rounds are used up
