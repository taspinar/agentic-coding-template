How the template evolved

We started with a manual workflow and gradually automated the steps that proved useful and repeatable.

The ideas behind the workflow are not new. The template combines established software engineering practices with AI coding tools and fits them into a development process on GitHub.

  1. Initial workflow
  2. Structured planning
  3. Independent verification
  4. Improved reliability
  5. Unattended execution

  1. Initial workflow

    The first version was mostly documents: instructions for agents, a few policies, a setup guide, and a rhythm of plan, act, and evaluate. A feature was planned in a GitHub issue, built in its own worktree, and read by a second agent. Developers had to move between the steps themselves.

    The first scripts took over what was the same every time: creating the issue of a feature, starting the work, and starting the review. Soon after, each review finding got an explicit decision, and the implementer fixed only what had been decided.

  2. Structured planning

    Until then the template assumed that you already knew what to build. A planning process was added before the first feature: from an idea to clear requirements, an architecture, and a roadmap.

  3. Independent verification

    Practical use revealed that some checks relied too heavily on the agent's own reports: that the tests had passed, that a review covered the current code, that a finding had been dealt with.

    These were replaced by records a script can check. The project's checks got one command. Reviews and decisions about findings became structured records, each linked to the version it was written for. Reviewers lost the ability to edit files. The plan got its own independent review and an approval linked to the approved version of the documents.

  4. Improved reliability

    Building real features brought practical problems to the surface, and each got an answer:

    • A session can end unexpectedly, so a feature can resume from a handoff note.
    • Verification ran more often than needed, so a successful run is reused for unchanged content.
    • A plan sometimes has to change after its approval, so there is a change process for it.
    • A second review only needs to read what changed.
    • A project created from a template does not receive later improvements, so a script brings them over.

  5. Unattended execution

    Once every step was a script, the steps could run in a row. One command now takes a feature from its issue to an open pull request without stopping for routine input. It ends at the pull request: it does not merge.

    Unattended work needed clearer rules. A script, not an agent, decides whether a step succeeded, and it retries a temporary failure. "Blocked" means only that a person has to decide. Reviews must stay up to date when the code or the base branch changes. And whether a change needs the owner's approval is no longer left to the agent that made the change.

What the order shows

  • Manual first. Deciding on findings, the planning loop, and the unattended run were each a manual routine before they were a script.
  • Evidence before automation. Recorded reviews and verification came before the command that runs a feature alone. Without them an unattended run would have had nothing to stop on.
  • Improvements driven by real-world use. Once real work depended on the template, most changes answered something that had gone wrong.

The template is still evolving. See Possible improvements for the ideas under consideration.
