History

The template did not start as a set of scripts. It started as a way of working, written down, and grew into one command per feature. Each step became a script only after it had been done by hand often enough to know what the script had to guarantee.

  1. Steps done by hand, written down

    The first version was mostly documents: instructions for agents, a few policies, a guide for setting up a repository, and a rhythm of plan, act, and evaluate. A feature was planned in an Issue, built in its own worktree, and read by a second agent. The person in the middle carried the results from one step to the next.

    The first scripts took over the parts that were the same every time: creating the Issue of a feature, starting the work, and starting the review. Soon after, the findings of a review got an explicit answer, the triage, and the implementer was held to fixing only what the triage had decided.

  2. A project starts with a planning

    Until then the template assumed that someone already knew what to build. That turned out to be the weakest assumption of all. A planning phase was added before the first feature: from a project idea to requirements, an architecture, and a roadmap of features.

  3. From trust to evidence

    Using the workflow showed where it relied on an agent's word: that the tests had passed, that a review covered the current code, that a finding had been dealt with. One by one these were replaced by something a script can check. The project's checks got one command. Reviews and triage decisions became structured records that are validated, and each was bound to the exact content it was written for, so that a later change makes it visibly stale. Reviewers lost the ability to write.

    The planning got the same treatment as a feature: an independent review of its own, a recorded decision for every finding, and an approval by the owner that is tied to the documents as they were approved. And the reports of reviews moved out of the repository and onto the Issue, where the work is discussed.

  4. The first real project

    Then the template was used to build something real: a physics course site with executable lessons and formal proofs. The first run produced a long list of findings, and most of what followed removed friction that only shows with real work.

    Sessions get interrupted, so a feature learned to resume from a handoff note without the previous conversation. Verification was running twice, so a pass is now recorded and reused for identical content. A planning has to change after it was approved, so there is a change cycle for it, and a lighter path for a small technical amendment. A second review round only needs to read what changed. And because a project made from a template does not receive the template's later improvements, a script now brings them over, touching only the files that belong to the template.

  5. One command, and the gate that makes it safe

    With every step scripted, the steps could run in a row. One command now takes a feature from its Issue to an open pull request without questions, and stops there.

    Running that overnight on a queue of features exposed what unattended work needs. A script, not an agent, has to decide whether a step succeeded, retry what was only a network error, and let the implementer repair a check that really fails. "Blocked" has to mean that a person must decide, and nothing else. A feature has to be reviewed against the base it started from, also when that base has moved on. And the decision whether a change needs the owner cannot be left to the agent that made it: a merge gate now decides from the files a change touches, with the reviewer's judgment on top, and an agent cannot talk its way past it.

What the order shows

  • By hand first. Triage, the planning loop, and the unattended run were each a manual routine before they were a script.
  • Evidence before automation. Bound reviews, validated records, and the recorded verification came before the command that runs a feature alone. Without them an unattended run would have had nothing to stop on.
  • Real use sets the agenda. Once a real project depended on the template, nearly every change answered something that had gone wrong there.
