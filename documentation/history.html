History

The template grew in one month from a set of documents and steps done by hand to one command per feature. Each step became a script only after it had been done by hand often enough to know what the script had to guarantee.

Every entry links to the pull request that made the change; its description and the Issue it closes hold the reasoning.

  1. 10–11 September 2026

    Steps done by hand, written down

    The first version is mostly documents: instructions for agents, policies, how to set up a repository, and a plan-act-evaluate rhythm. A feature is planned in an Issue, built in a worktree, and reviewed by a second agent, with the human copying results from one step to the next.

    • Repository setup and the first planning phase #1 #2 #3 #4
    • A script to create a feature Issue, and scripts to start and review a feature #5 #8
    • Review findings get a triage, and an approved triage is applied by the implementer #12 #14

  2. 15 September 2026

    A project starts with a planning

    Until here the template assumed that someone already knew what to build. The bootstrap planning adds the step before the first feature: from a project idea to requirements, an architecture, and a roadmap.

    • Project bootstrap planning #22

  3. 2–3 October 2026

    From trust to evidence

    Two weeks of use showed where the workflow relied on an agent's word. This round replaces that with data a script can check: reviews and triages become validated JSON, each is bound to the exact content it read, and the planning gets its own independent review, recorded decisions, and an approval tied to the documents.

    • Reliable project verification with one command, and a check of the local prerequisites #31 #34
    • One place to configure agents, and reviewers that cannot write #35
    • Validated JSON for reviews and triage, bound to the reviewed version by a fingerprint #39 #42
    • Reports published on the Issue instead of committed #43
    • A feature Issue created from its roadmap entry #44
    • The planning loop: review, revise with a decision per finding, finish with an approval #49 #50 #51
    • finish-feature.sh as the closing step; the workflow documented in three views; cleanup of merged worktrees #52 #54 #57

  4. 6–8 October 2026

    The first real project

    A physics course site is built with the template, and the first run produces a list of findings. Most changes of these days remove friction that only shows with real work: sessions that are interrupted, verifications that run twice, a planning that has to change after it was approved, and projects that fall behind the template.

    • Fixes from the first real run; the template's own tests run only when the workflow changed #61 #69
    • A setup script for a new worktree; publishing a feature with one command #71 #73
    • A passed verification is recorded, required for a review, and not repeated #74 #83
    • sync-template.sh brings template changes into an existing project #76
    • An interrupted feature resumes without the previous chat #77
    • An approved planning changes through a change cycle, or a small amendment #79 #80
    • A re-review can cover only the changes since the previous round #81

  5. 9–10 October 2026

    One command, and the gate that makes it safe

    With every step scripted, the steps can run in a row. run-feature.sh takes a feature from its Issue to an open pull request without questions. Running it overnight on a queue of features exposed what unattended work needs: a script, not an agent, that decides whether a step succeeded, and a merge gate that an agent cannot talk its way past.

    • An unattended permission profile for agents, and run-feature.sh #89 #91
    • "Blocked" means a person has to decide, not that a verification is unfinished #95
    • A feature is reviewed against the base it was created from #93
    • The planning approval stays current when a feature updates the architecture #96
    • The merge approval gate: protected paths, decision records, and the reviewer's impact classification #100
    • The scripts decide the outcome of a step, and retry or repair it #101

What the order shows

  • By hand first. Triage, the planning loop, and the unattended run were each a manual routine before they were a script.
  • Evidence before automation. Fingerprints, validated records, and the recorded verification came a week before the command that runs a feature alone. Without them an unattended run would have had nothing to stop on.
  • Real use sets the agenda. From 6 October on, nearly every change answers something that went wrong in the project built with the template.
