How the template evolved

The template started as a basic workflow for planning, implementation, and independent review. Each step became a script only after it had been done by hand often enough to know what the script had to guarantee.

The ideas behind the workflow are not new. The template combines established software engineering practices with AI coding tools and fits them into a development process on GitHub.

  1. A workflow, written down

    The first version was mostly documents: instructions for agents, a few policies, a guide for setting up a repository, and a rhythm of plan, act, and evaluate. A feature was planned in a GitHub issue, built in its own worktree, and read by a second agent. The developer carried the results from one step to the next.

    The first scripts took over what was the same every time: creating the issue of a feature, starting the work, and starting the review. Soon after, each review finding got an explicit decision, and the implementer fixed only what had been decided.

  2. Planning before development

    Until then the template assumed that you already knew what to build. That was its weakest assumption. A planning process was added before the first feature: from an idea to clear requirements, an architecture, and a roadmap.

  3. More reliable reviews and approvals

    Using the workflow showed where it relied on an agent's word: that the tests had passed, that a review covered the current code, that a finding had been dealt with. These were replaced, one by one, by something a script can check. The project's checks got one command. Reviews and decisions about findings became structured records, each linked to the version it was written for, so that a later change makes it visibly outdated. Reviewers lost the ability to edit files.

    The plan got the same treatment as a feature: an independent review, a recorded decision for every finding, and an approval linked to the approved version of the documents.

  4. Improvements from regular use

    Building real features with the template brought practical problems to the surface. A session can end unexpectedly, so a feature can now resume from a handoff note. Verification ran more often than needed, so a successful run is recorded and reused for unchanged content. A plan sometimes has to change after its approval, so there is a change process for it. A second review only needs to read what changed. And because a project created from a template does not receive later improvements, a script now brings them over.

  5. Unattended feature execution

    Once every step was a script, the steps could run in a row. One command now takes a feature from its issue to an open pull request without stopping for routine input. It still ends at the pull request: it does not merge.

    Running features this way showed what unattended work needs. A script, not an agent, decides whether a step succeeded; it retries a temporary failure and lets the implementer repair a check that really fails. "Blocked" means only that a person has to decide. A feature is reviewed against the branch it started from, also when that branch has moved on. And whether a change needs the owner's approval is no longer left to the agent that made the change.

What the order shows

  • By hand first. Deciding on findings, the planning loop, and the unattended run were each a manual routine before they were a script.
  • Evidence before automation. Recorded reviews and verification came before the command that runs a feature alone. Without them an unattended run would have had nothing to stop on.
  • Use sets the agenda. Once real work depended on the template, nearly every change answered something that had gone wrong.

The template is still evolving. See Possible improvements for the ideas under consideration.
